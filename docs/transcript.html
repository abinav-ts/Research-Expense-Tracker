Why it's a good project

  • The problem is real and specific. Researchers hand over entire bank statements to prove one conference trip, which exposes unrelated spending. A tool that lets them prove only the relevant expenses is a clear privacy and compliance win.
  • It suits spec-driven development well. The domain has clear actors, rules (grant categories, caps, deadlines) and testable outputs, so you can write a crisp spec first and build against it.
  • It has a good demo story: "before, a bank statement with personal data; after, a clean claim pack."

The risk is scope. Anything involving bank integrations (Account Aggregator, UPI/bank APIs), OCR accuracy, or real authentication will eat your 36 hours. Avoid those.

Must-have features (the MVP)

  1. Trip and grant setup. Create a trip (conference, dates, destination) linked to a grant, with budget categories such as registration, airfare, lodging, local transport, meals and visa.
  2. Expense capture. Add an expense with amount, currency, date, category, and a receipt photo or PDF upload. Manual entry is fine. Optional: import a bank statement CSV and let the user tick which rows belong to the trip.
  3. Tagging for privacy. This is your core differentiator. Only expenses tagged to a trip go into the claim. Everything else never leaves the user's side.
  4. Rule checks. Flag expenses outside the trip dates, over category caps, missing receipts, or in non-eligible categories. Making these rules configurable is where spec-driven development shines.
  5. Claim pack export. Generate a PDF (or PDF plus CSV) summarizing the claim: trip details, itemized expenses with receipts attached, totals per category, and a declaration line. No bank statement needed.
  6. Reviewer view (simple). A read-only link or page where the grant officer can see the claim and mark items approved or rejected with a comment. Even a basic version makes the demo much stronger.

Nice-to-haves, only if time remains

  • Foreign currency conversion using a fixed rate table you enter yourself.
  • Per-diem calculation.
  • Duplicate-receipt detection (hash of file or amount plus date).
  • Simple audit log of edits.

What to skip

Bank API integration, automatic OCR (mention it as future work), multi-institution tenancy, real authentication (use a simple login or a fake user switch), and mobile apps (make a responsive web app instead).

Suggested stack: something you already know. For example, a React or plain HTML front end with FastAPI or Node, SQLite for storage, and a PDF library such as ReportLab or WeasyPrint. Keep deployment to one command.
